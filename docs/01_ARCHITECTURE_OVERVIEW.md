# System Architecture Overview

> [!NOTE]
> This document explains the high-level architecture of **Unknown Intelligence** (Aurora Intelligence), focusing on the backend stack and how components interact.

## 1. Core Stack
The product is built on a highly concurrent, asynchronous Python backend tailored for machine learning orchestration and heavy data processing.

- **Backend Framework**: `FastAPI` (Python) for asynchronous endpoints.
- **Document Store**: `MongoDB` (accessed asynchronously via the `motor` library). We also use a mocked adapter (`mongomock-motor`) for local testing without requiring a live MongoDB instance (using `MONGO_URI="mock"`).
- **Vector Database (RAG)**: `Milvus` (via `pymilvus`) for semantic search, similarity matching, and handling large-scale embeddings for the discovery engine.
- **AI Models**: Designed to utilize frontier models (like Gemini) via the Antigravity agentic frameworks to reason over the dataset.
- **Data processing**: `Jupyter Notebooks` (`train.ipynb`) and `scikit-learn` (Random Forest) for dataset baseline generation and statistical anomaly detection.

## 2. System Flow

The architecture is designed to support the **proactive** nature of the application. Unlike standard reactive applications, the flow is:

```mermaid
graph TD
    A[Data Ingestion (ingest.py)] -->|Normalizes & Deduplicates| B(State Layer: MongoDB)
    A -->|Chunks & Embeds| C(Vector Store: Milvus)
    B --> D{Candidate Generator}
    D -->|Change/Contradiction Detection| E(Significance Filter)
    E -->|High Significance| F[Investigation Engine]
    C -.->|Semantic Evidence| F
    F -->|Tests Hypotheses| G[Findings & Discoveries]
    G --> H[FastAPI Endpoints]
    H --> I[Frontend UI]
```

## 3. Database Schema (MongoDB)

The `motor` database is organized into the following primary collections to support provenance and evidence tracking:

1. **`entities`**: The core objects being monitored.
2. **`events`**: Timestamped occurrences related to entities.
3. **`observations`**: The actual content/data attached to events.
4. **`findings`**: The finalized, verified discoveries generated by the system.
5. **`baselines`**: Expected operating ranges or historical averages used by the candidate generator.

## 4. Scalability & Pressure Testing

The system is continuously verified using `backend/pressure_test.py`. Current benchmarks demonstrate the system successfully handling **200 concurrent requests per second** with **0 failures**, ensuring the asynchronous `FastAPI + Motor` setup scales effectively during intense data ingestion or multi-agent investigations.
